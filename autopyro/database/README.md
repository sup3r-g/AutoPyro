# Работа с базами данных

Весь программный код приложения для БД собран в пакете `autopyro.database`.

| Модуль / папка | Назначение |
| --- | --- |
| `access.py` | Проверка прав и read-only транзакций |
| `connection.py` | Параметры окружения / `.env`, подключение PostgreSQL |
| `readers.py` | Чтение исходных снимков SQLite и PostgreSQL |
| `geochem.py` | Каталог геохимических полей, чтение профилей, сборка проекта |
| `sources.py` | Адаптеры источников, идентичность и происхождение записей |
| `refresh.py` | Сравнение и применение обновлений снимков |
| `storage.py` | SQLite-хранилище `.apyro`, блокировки и атомарное сохранение |
| `history.py` | Упорядоченные события и общий реестр снимков протоколов |
| `preferences.py` | Подстановка параметров подключения и пароль в памяти сеанса |
| `ui/` | Диалоги снимков, обновления, геохимической БД и компонент настройки подключения |
| `tools/` | Генерация схемы, импорт Parquet / литостратиграфии, настройка и проверка ролей |

Основные модули не зависят от Qt. Подпапка `ui` использует общие компоненты
`autopyro.ui` и вызывается главным окном. Общие настройки приложения по-прежнему
хранятся в `QSettings`; обработка параметров подключения находится здесь.
Импорт `autopyro.database` сам по себе не загружает Qt и драйвер PostgreSQL.

Новый код импортирует, например:

```python
from autopyro.database.readers import read_sqlite, read_postgres_snapshot
from autopyro.database.storage import save_project, load_payload
from autopyro.database.ui.snapshot import DatabaseDialog
```

Прежние `autopyro.storage`, `autopyro.database_access`, `autopyro.database_sources`,
`autopyro.database_refresh`, `autopyro.geochem_database` и `autopyro.ui.database.*`
поддерживаются единым механизмом совместимости без отдельных файлов-обёрток.
Экспорты читателей из `autopyro.io` также сохранены.

## Версии локального проекта

Новые сохранения используют SQLite v4. Таблицы `history_events` и
`history_protocols` хранят порядок действий и единственную копию каждого
архивного протокола; внешние ключи, контрольные суммы, число и непрерывность
позиций проверяются при чтении. В памяти остаётся обычный список событий.

В v4 таблицы `stored_protocols`/`stored_protocol_parts` дополнительно хранят
вложенные `interpolation_protocol` колонок и событий. Таблицы
`column_protocols`/`history_nested_protocols` связывают владельцев с содержимым.
Это отдельные SQL-ссылки; пользовательские поля JSON не распознаются как
служебные маркеры. В JSON владельца остаётся null на прежнем месте поля.
При загрузке ссылка допустима лишь при наличии такого поля с null.

JSON v1 и SQLite v2/v3 открываются без перезаписи исходного файла. Перед первым
обычным сохранением поверх старого формата создаётся точная копия
`.v1-<hash>.bak`, `.v2-<hash>.bak` или `.v3-<hash>.bak`. Неудачная запись оставляет исходный файл;
повторное сохранение использует уже проверенную резервную копию. Временные
копии восстановления не мигрируют основной файл. Старые версии приложения,
понимающие только v2/v3, не открывают v4; для них сохраняется исходная резервная
копия. Источники лабораторных данных по-прежнему доступны только для чтения.

## Административные утилиты

Запускаются из корня репозитория:

```powershell
.\.venv\Scripts\python.exe -m autopyro.database.tools.generate_schema path/to/dtypes.txt
.\.venv\Scripts\python.exe -m autopyro.database.tools.import_parquet path/to/data.parquet --inspect
.\.venv\Scripts\python.exe -m autopyro.database.tools.import_lithostratigraphy path/to/intervals.xlsx
.\.venv\Scripts\python.exe -m autopyro.database.tools.configure_users
.\.venv\Scripts\python.exe -m autopyro.database.tools.validate_users
```

Утилиты запускаются из checkout репозитория с SQL и каталогами. Офлайн-комплект
настольного клиента содержит функции чтения и обновления снимков. Для Parquet нужен
`pyarrow`, как и до переноса. SQL-схема, миграции, каталог полей, отчёты импорта
и резервные копии остаются в корневой папке `database/`. Пути к ним и к `.env`
сохранены. Подключение к БД и административные операции происходят только
при явном запуске соответствующей команды.

## Память загрузки научных записей

SQLite-загрузчик передаёт в `MeasurementStore.from_sqlite_payloads` итераторы
`(id, словарь полей)` и создаёт dataclass-записи по мере чтения. Рабочие
ссылки читаются сразу в итоговый словарь после восстановления записей.
`MeasurementStore.from_dict` сохраняется для JSON и снимков.

При создании записи реестр переиспользует строки уже восстановленных UUID,
статусов и единиц. Это локальная операция загрузки, без глобального interning.
Сами измерения, истории и метаданные не объединяются. Неизвестные ссылки
и несоответствия ключа/UUID сохраняются до штатной валидации.

Колонки и события SQLite-журнала дополнительно читаются через локальный
`JsonStringPool`. Он повторно использует равные короткие строки (до 128
символов) и неизменяемый текст архивов, включая UUID во вложенных протоколах.
В v4 реестр декодирует каждое уникальное содержимое один раз; дальнейшим
владельцам копируются только изменяемые JSON-контейнеры. В v2/v3 остаётся
обработка отдельных прежних записей.
Словари/списки остаются независимыми. Обработчик JSON меняет только ссылки
на строки; словарь пересоздаётся лишь для замены равных ключей UUID с
сохранением их порядка. Научные записи читаются обычным JSON-декодером;
их ключи используют уже известные строки протоколов, а штатная загрузка
MeasurementStore по-прежнему проверяет и связывает равные ссылки.

Пул содержит максимум миллион строк; после достижения лимита новые строки
не запоминаются, уже известные продолжают использоваться. Чтение научных
записей не расширяет пул. Он существует только во время загрузки, без
sys.intern или глобального кеша. Длинный свободный
текст не помещается в пул. Архивы остаются сжатыми и не распаковываются
ради объединения строк. Вложенные изменяемые протоколы не объединяются.

При чтении строк таблицы ключи `values` и `original`, равные ID существующих
колонок, используют уже загруженные строки этих ID. Для этого достаточно
отдельного словаря размером с число колонок; он не зависит от размера пула
протоколов. Значения, неизвестные ключи и порядок сохраняются. Словари строк
и их изменяемые значения не объединяются. Проверка состава строки остаётся
обязательной. Это применяется при открытии SQLite v2/v3/v4 без записи файла
и изменения формата; JSON v1 читается прежним способом.

Для отдельного контроля этой экономии памяти повторить open одного файла
с `--plain-row-keys` и без него. Флаг отключает только повторное использование
ключей строк в процессе утилиты; обработка протоколов и проверки сохраняются.
Не запускать сравниваемые процессы одновременно.

Сравнение открытия одного и того же большого синтетического файла:

```powershell
.venv\Scripts\python.exe tools/benchmark_large_project_storage.py open tmp/large.apyro --plain-strings --replay --output tmp/strings-control.json
.venv\Scripts\python.exe tools/benchmark_large_project_storage.py open tmp/large.apyro --replay --output tmp/strings-shared.json
```

`--plain-strings` действует только в процессе инструмента и только на open:
возвращает прежний JSON-декодер без пула. SQL, научные данные и валидация
не подменяются. Повторное использование строк экономит память, но требует
дополнительной обработки при открытии; оценивать следует обе метрики.

Воспроизводимый замер на временном синтетическом SQLite-проекте:

```powershell
.venv\Scripts\python.exe -m tools.benchmark_science_loading --rows 1000 --extra-columns 75 --output tmp/science-load.json
```

Инструмент сверяет полное содержимое после открытия и удаляет только свой
временный проект. Время включает валидацию; построение/сохранение входов
и контрольная сумма исключены. Размер графа объектов и рабочий набор
процесса — разные метрики. Накопительный пик включает построение и запись
входного файла; файл только что сохранён, холодный дисковый кеш не проверяется.

## Запись больших проектов

`storage._write_database` передаёт записи в SQLite итераторами. В памяти не
накапливаются списки JSON всех строк/измерений/рабочих ссылок. `write_history`
записывает каждое событие до сериализации следующего; реестр неизменяемых
архивов истории остаётся прежним. Все вставки входят в одну транзакцию
временного файла, а замена основного файла выполняется только после успеха.

Два поисковых индекса (`measurement_sample_property`, `analysis_sample`)
строятся после вставки строк, перед проверкой FK и commit. Это снижает
стоимость поштучного обновления индексов. PRIMARY KEY, UNIQUE и внешние ключи
действуют при вставке; итоговая схема и версия формата остаются прежними.
DDL выполняется через execute в той же транзакции, без промежуточного commit.
Ошибка построения индекса оставляет прежний файл и digest нетронутыми.
На синтетическом наборе 10 тыс. × 80 полный Save занял 39.12 вместо 46.46 с,
пик процесса к концу Save вырос с 1.690 до 1.824 ГБ. Один проход Qt offscreen
с наблюдателями; это измерение, не гарантия ускорения на любом проекте.

`encode_record` кодирует объявленные поля dataclass напрямую через стандартный
JSONEncoder. Предварительного `asdict` и глубокого копирования метаданных
колонки нет. Вложенные dataclass-записи, Unicode, большие целые и tuple
сохраняют прежнее JSON-представление; дополнительные динамические атрибуты
по-прежнему не входят в файл. Неконечные числа и неподдерживаемые значения
отклоняются. JSON обычной записи всё ещё собирается целиком; крупные вложенные
протоколы в v4 вынесены в реестр. Блокировки и атомарная замена сохранены.

Во время одной записи файла используется один `_RecordEncoder`. Он хранит
до 32 описаний полей по типу dataclass, а не по имени класса. Экземпляры
и значения не кешируются: поля читаются заново у каждой записи. ClassVar,
InitVar и дополнительные динамические атрибуты исключаются как прежде.
Кеш живёт только до окончания save; цикл или неконечное число в одной
записи не оставляют маркеры рекурсии в следующем вызове кодировщика.

Соединение записи временной SQLite-БД получает бюджет страничного
кеша 256 МиБ (`WRITE_CACHE_KIB`), чтобы снизить повторные чтения страниц
индексов при проверке внешних ключей. Это не предвыделение памяти и не
лимит всего процесса. При закрытии соединения кеш освобождается. Foreign keys, journal,
synchronous, commit/fsync и атомарная замена не ослабляются.

При открытии SQLite-проекта от 512 МиБ кеш увеличивается до 128 МиБ
на время проверок целостности. Перед восстановлением объектов SQLite
освобождает лишние страницы, а лимит возвращается к 32 МиБ.

Сохранение и открытие большого синтетического проекта в отдельных процессах:

```powershell
.venv\Scripts\python.exe tools/benchmark_large_project_storage.py save tmp/large.apyro --rows 100000 --output tmp/large-save.json
.venv\Scripts\python.exe tools/benchmark_large_project_storage.py open tmp/large.apyro --replay --output tmp/large-open.json
```

`--profile` записывает cProfile в файл рядом с JSON; эти времена включают
профилировщик и не считаются обычной задержкой. `--inline-protocol` (только
полный save) сохраняет обычный протокол вместо сжатия для профилирования
того же пути на меньшей выборке. Научный расчёт и сверка остаются прежними.
Контроль `--plain-records --write-cache-mib 0` возвращает в процессе утилиты
прежнее создание кодировщика/описания полей для каждой записи и стандартный
кеш SQLite. `--write-cache-mib N` задаёт бюджет записи только в эксперименте;
0 оставляет стандартную настройку SQLite. Флаги и профилирование записываются
в результат. В интерфейсе приложения эти контрольные режимы не включаются.

Для save нужен новый путь. Инструмент создаёт пять исходных колонок, PCHIP
по отфильтрованной глубине и два независимых события применения через undo/
redo. Рядом создаётся `.verification.json` с контрольной суммой содержимого.
Open сверяет её, проверяет неизменность файла и при `--replay` воспроизводит
все предложения. Проверка содержимого потоковая по записям и протоколам;
время подготовки/сверки/replay не входит во время save/open. Пик процесса
накопительный; на save он включает подготовку входов. Замер без tracemalloc,
показанного рабочего стола и оценки задержек GUI. Чтение только что созданного
файла не проверяет холодный дисковый кеш. Инструмент не удаляет свои файлы.

В памяти копии изменяемых протоколов колонок и событий независимы. На диске
одинаковая последовательность JSON-байтов (включая порядок ключей) хранится
один раз в реестре v4; собственный checksum протокола не используется как ID.
ID — SHA-256 вида и всего содержимого. JSON кодируется компактно порциями,
записывается BLOB-частями до 1 МиБ; при повторном проходе проверяется, что
входы не изменились. Загрузка проверяет размеры, позиции/число частей,
SHA-256, внешние ключи, владельцев и отсутствие неиспользуемых протоколов.
Только затем содержимое декодируется. Архивы остаются текстом без распаковки.

На один реестрируемый протокол допускается до 1 ГиБ обычных байтов хранения.
Это отдельный лимит v4, не увеличение 256-МиБ лимита распаковки audit.py.
Более крупные значения, маленькие JSON (<64 КиБ) и расширения, которые
обычный кодировщик протоколов не поддерживает, остаются в прежнем inline JSON.
Сериализация обычных записей затем обрабатывает допустимые расширения либо
отклоняет ошибочные данные; реестр не отбрасывает содержимое. Часть имеет
фиксированный размер 1 МиБ (последняя может быть короче); изменение размера
потребует новой версии формата. Отдельные огромные значения и декодирование
уникального протокола всё ещё могут требовать значительной памяти.

`--table-only` оставляет исходную таблицу и измерения без интерполяции.
Для контрольного save можно добавить `--eager-control`: только в процессе
инструмента возвращаются прежние `asdict` и материализация аргументов
executemany в списки. Научные данные, SQL, транзакции и проверки сохраняются;
флаг записывается в результат. Этот контроль разрешён только для table-only
save, где нет больших вложенных протоколов. Режим не включается в приложении.

`--extra-columns N` добавляет исходные числовые показатели к пяти стандартным.
Сценарий PCHIP использует те же входы Well/Depth/S2, остальные показатели
также сохраняются и входят в полную сверку. Например, `--rows 30000
--extra-columns 75` создаёт 80 исходных колонок и 2.4 млн измерений.
При open число исходных колонок берётся из файла, а не из CLI-параметров.

Для памяти живой истории есть отдельный инструмент без записи проекта:

```powershell
.venv\Scripts\python.exe tools/benchmark_live_history.py --rows 100000 --redos 3 --legacy-protocol --output tmp/history-legacy.json
.venv\Scripts\python.exe tools/benchmark_live_history.py --rows 100000 --redos 3 --output tmp/history-compact.json
```

Контроль --legacy-protocol оставляет полные записи измерений прежних v1/v2
только в процессе утилиты. Обычный режим допускает кодирование v3 с явными
null по умолчанию (описано в UI README). --inline-protocol дополнительно
отключает архивирование для диагностики. После каждого undo/redo сверяются
все исходные значения, UUID и новый столбец. Время команды не включает GC
и проверки; память снимается после их завершения/обработки событий Qt.
Разбор архива и replay выполняются после замера памяти. Нет полного
рабочего стола, оценки UI-пауз и сохранения файла. Рост рабочего набора
не равен размеру логического графа: учитываются и резерв/повторное
использование памяти Python. Метаданные предложений/области по-прежнему
копируются в каждое событие; вся история не становится ограниченной.

На подходящих больших наборах кодирование v3 может вернуть протокол в
прежний 256-МиБ лимит архива. Лимит и формат архива не меняются. Если даже
компактный протокол слишком велик или не подходит для архива, сохраняется
прежний fallback inline JSON и независимое копирование истории. SQLite v4
хранит как эти словари, так и архивные строки без изменения их содержимого.
