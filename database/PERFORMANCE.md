## Что изменено

Изменения внесены новыми зарегистрированными миграциями; прежние SQL-файлы
истории не редактировались:

- **011:** в `v_pyrolysis_report` соответствие семи полей группы определяется
  один раз. Каждый запуск читает нужные результаты по первичному ключу, без
  повторного соединения со всем справочником полей.
- **011:** `v_geochemical_availability` сначала агрегирует по исходной скважине,
  пакету импорта, полю и datum. Названия и семантические справочники присоединяются
  к уже сокращённому набору. Размер ключей группировки уменьшен.
- **011:** `v_sample_lithostrat_status` использует общую группировку попаданий
  по пробам. Добавлен индекс `interpretation_reference_depth_idx` по версии,
  типу глубины, datum и границам интервала. Он обслуживает проверку совместимости
  систем глубин и поиск интервалов. В исходном плане заметную часть времени
  занимала JIT-компиляция, вызванная высокой расчётной стоимостью корреляции;
  уменьшение стоимости отключило дорогие этапы JIT inlining/optimization для
  этого плана и сократило компиляцию примерно с 445 до 30 мс без изменения
  серверных настроек.
- **012:** `v_analysis_result_semantic` получает `source_field_id` напрямую,
  без второго соединения того же справочника по группе и названию.
- **013:** в `v_geochemical_measurement` фильтруемые пробы включены в начальную
  группу соединений. При большом количестве справочников стандартный
  `join_collapse_limit` ограничивал перебор порядка соединений, и старый план
  обрабатывал все результаты до применения фильтра по скважине.

Обычные представления сохраняют актуальность сразу после изменения исходных
данных или сопоставлений. Материализованные таблицы, дополнительное обновление
агрегатов и глобальные изменения work_mem/jit/join_collapse_limit не вводились.
Новый индекс поддерживается PostgreSQL при обычных изменениях интервалов.
Названия, порядок и типы колонок старых представлений сохранены, включая
все методы, повторы, источники, отсутствующие значения и множественные попадания.

## Проверка корректности и совместимости

Валидатор восстанавливает исходные определения в своей транзакции, сохраняет
полные выборки и сравнивает их с оптимизированными через EXCEPT ALL в обе стороны.
Это проверяет значения, NULL, число строк и кратность дубликатов, включая все
1 056 734 строки семантического и длинного представлений. Транзакция откатывается.
Проверены также доступ readonly, повторное применение SQL и синтетические
привязки с границами, частичными попаданиями и разными рангами.
52 автоматических теста прошли, реальный запрос каталога приложения работает.

В текущей базе рабочие интерпретации ещё не выбраны, метаданные качества пока
не заполнены. Поэтому скорость статусов и сводки качества относится именно
к этому состоянию. Корректность заполненных привязок проверена синтетическими
данными с откатом; производительность при массовом заполнении нужно измерить
повторно. Исходные данные и выбранные настройки пользователей не менялись.

## Повторение измерений

Из корня проекта, обычное подключение readonly:

```powershell
.venv/Scripts/python.exe -m autopyro.database.tools.benchmark_analytics --output database/performance/new-run.json --repeats 3
```

Лимит каждого запроса по умолчанию 45 секунд; при превышении в отчёте сохраняется
ошибка. Можно задать `--timeout-seconds`. Результаты передаются через EXPLAIN,
а не выгружаются целиком на клиент. Полные планы остаются в локальном JSON.

Проверка равенства и сценариев привязки (административное подключение, все
временные изменения откатываются):

```powershell
.venv/Scripts/python.exe -m autopyro.database.tools.validate_analytical_performance
.venv/Scripts/python.exe -m autopyro.database.tools.validate_sample_lithostrat_matching --optimized
```

Проверка полного равенства использует временные таблицы и сортировки: требует
временного дискового пространства и может занимать больше времени, чем обычная
аналитическая выборка. Запускать при отсутствии параллельных изменений схемы.
Для установки изменений на другой базе используется стандартная команда
`python -m autopyro.database.tools.migrate --apply`.

## Проверка регрессий после следующих изменений

Сохранённый `performance/after.json` можно использовать как текущий ориентир.
После следующей миграции запустите новый замер, а затем сравнение:

```powershell
.venv/Scripts/python.exe -m autopyro.database.tools.benchmark_analytics --output database/performance/new-run.json --repeats 3
.venv/Scripts/python.exe -m autopyro.database.tools.compare_analytics database/performance/after.json database/performance/new-run.json --output database/performance/new-comparison.json
```

Сравнение не подключается к базе и не меняет исходные отчёты. Медианы заново
вычисляются из отдельных времён и сверяются с EXPLAIN; готовое поле median_ms
не принимается на веру. Требуется не меньше трёх прогонов. Замедление считается
существенным при одновременном превышении двух порогов: более 25% и более 20 мс.
Так одиночный выброс или рост с 1 до 2 мс не превращается в регрессию.
Пороги можно изменить через `--ratio 1.5 --min-increase-ms 50`.

Успешное сравнение требует одинаковых версий PostgreSQL, сохранённых настроек,
количества проб/запусков/результатов, идентификаторов выбранной пробы/скважины,
набора SQL-запросов, их параметров и количества возвращённых строк. Неполные
отчёты, некорректные времена и изменение результата по числу строк отвергаются.
Таймаут запроса в новом отчёте считается неуспехом проверки даже при наличии
частично успешных прогонов. Неуспешный исходный отчёт использовать нельзя.

Коды завершения сравнения:

- 0: существенных регрессий нет.
- 1: обнаружено замедление или ошибка/таймаут нового запроса.
- 2: отчёты повреждены, неполны или несопоставимы.

Это проверка скорости и сопоставимости измерений, а не доказательство равенства
данных. Одинаковые счётчики строк не гарантируют одинаковые значения или их
распределение. Для проверки значений используйте валидаторы выше. Загрузка CPU,
диска, кеш и настройки Docker, не вошедшие в отчёт, также влияют на время.
Сравнивайте на том же оборудовании без параллельных тестов/импортов. Повторяйте
замер при обнаружении регрессии и исследуйте планы до изменения SQL или порогов.
Не обновляйте исходный ориентир автоматически после неуспешной проверки.

Замеры выполняются ролью readonly с таймаутом подключения 8 секунд. Docker и
PostgreSQL должны быть запущены. Созданные JSON-файлы предназначены для локального
анализа; настраивать фоновую службу или расписание для этой проверки не требуется.

Практическая проверка после запуска остановленного Docker: первый свежий отчёт
`performance/regression-current.json` отметил выборку по скважине как замедлившуюся
с 99,883 до 127,358 мс. Исходный ориентир не менялся. Повторный отдельный замер
из пяти прогонов (`performance/regression-repeat.json`) дал 106,617 мс; все
11 запросов прошли пороги. Оба результата сравнения сохранены в
`performance/regression-comparison.json` и
`performance/regression-repeat-comparison.json`. Сигнал первого прогона не
подтвердился при повторении и не стал поводом для дополнительного изменения SQL.
