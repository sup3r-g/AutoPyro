# Экспертная проверка показателей, единиц и методов

Миграция 014 добавляет журнал решений без изменения исходных значений,
названий, типов и прежних интерфейсов приложения. На текущих данных подготовлен
пакет `catalog_review/2026-11-05_initial`:

- [CANDIDATES.md](catalog_review/2026-11-05_initial/CANDIDATES.md): 778 групп
  совпадающих названий/единиц/типов (769 числовых, 9 текстовых).
- [catalog-snapshot.json](catalog_review/2026-11-05_initial/catalog-snapshot.json):
  4 178 исходных аналитических полей с текущими сопоставлениями, количеством
  результатов и контрольными отпечатками; 4 178 показателей, 32 единицы, 51 метод.
- [review-decisions.json](catalog_review/2026-11-05_initial/review-decisions.json):
  пустой шаблон для явных решений эксперта. Пустой файл не может утвердить данные.

Кандидаты сгруппированы строго по исходному названию, строке единиц и pandas-типу.
Это подсказки для проверки, а не научно подтверждённые эквивалентности. Например,
TOC встречается в 10 исходных группах с 23 970 результатами, S1/S2 — в 9 группах.
Различия методик, подготовки и основы пересчёта нужно проверить по документам.
Текстовые Lab, Date и аналогичные поля могут быть метаданными, а не показателями.
Синонимы с различающимися названиями/единицами в эти группы автоматически не входят.

## Экспорт нового пакета

```powershell
.venv/Scripts/python.exe -m autopyro.database.tools.catalog_review export --output-dir database/catalog_review/new-review
```

Экспорт использует readonly и согласованный read-only снимок данных. Каталог
назначения должен отсутствовать: отредактированные экспертные решения не
перезаписываются. Пакет не содержит значений отдельных проб или паролей.

## Формат экспертного решения

В корневом объекте обязательны `schema_version=1`, `reviewer`, `evidence`,
массивы `catalogs` и `mappings`. Автор и проверяемый источник (документ, протокол,
страница, раздел) обязательны. Хотя бы одно явное решение должно присутствовать.
Инструмент сохраняет заявленного эксперта и реальную роль PostgreSQL, но
не проверяет подлинность подписи или достоверность документа за эксперта.

`catalogs` позволяет создать новый канонический элемент или подтвердить
существующий. Каждое такое решение выставляет `reviewed=true` только этому элементу.

- `kind`: indicator, unit или method.
- `code`: устойчивый код; импортные префиксы source:, source-field: и source-group:
  зарезервированы для автоматически созданных записей.
- `expected`: NULL для нового кода; для существующего — его отпечаток из
  раздела catalogs снимка.
- `label` и `description`: обязательны при создании. label — название показателя/
  метода либо символ единицы. При подтверждении существующей записи их можно
  опустить. Изменять общую запись через подтверждение нельзя: создайте новый код.

`mappings` содержит решения для отдельных исходных полей:

- `source_field_id`: целочисленный ID из fields снимка.
- `expected`: отпечаток из того же элемента fields, не отпечаток показателя.
- `indicator_code`: существующий или создаваемый в этом решении показатель.
- `unit_code`/`method_code`: коды единицы/метода либо явный NULL, если неизвестны.
- `note`: строка с пояснением (может быть пустой, если достаточно общего evidence).

Сопоставление получает `reviewed=true`. Подтверждение сопоставления не
подтверждает автоматически все связанные единицы/методы: для них нужны отдельные
catalogs-решения. Текущие отдельные признаки indicator_reviewed/unit_reviewed/
method_reviewed в аналитических представлениях продолжают отражать это различие.

Пример формы файла (заменить ID, отпечатки, коды и источники после проверки):

```json
{
  "schema_version": 1,
  "reviewer": "ФИО эксперта",
  "evidence": "Документ, редакция, раздел и страница",
  "catalogs": [
    {
      "kind": "indicator",
      "code": "canonical:organic_carbon_total",
      "expected": null,
      "label": "Общий органический углерод",
      "description": "Определение показателя и подтверждённая основа выражения результата"
    }
  ],
  "mappings": [
    {
      "source_field_id": 123,
      "expected": "<64 шестнадцатеричных символа из fields выбранного снимка>",
      "indicator_code": "canonical:organic_carbon_total",
      "unit_code": "<точный код из catalogs.unit>",
      "method_code": "<точный код из catalogs.method>",
      "note": "Обоснование сопоставления конкретного исходного поля"
    }
  ]
}
```

Это форма, а не готовое научное решение для поля 123. Несколько полей можно
связать с одним показателем, сохранив разные методы и единицы. Числа при этом
не пересчитываются. Отнесение к канонической единице допустимо только после
подтверждения, что единица уже соответствует исходным значениям; преобразование
масштаба/основы выражения — отдельная задача и не выполняется этим инструментом.

## Проверка и применение

```powershell
# Пробное применение с обязательным откатом:
.venv/Scripts/python.exe -m autopyro.database.tools.catalog_review apply database/catalog_review/new-review/review-decisions.json

# Зафиксировать подготовленное решение:
.venv/Scripts/python.exe -m autopyro.database.tools.catalog_review apply database/catalog_review/new-review/review-decisions.json --commit
```

Для применения используется admin; исходный файл и цифровые отпечатки проверяются
заново и при --commit. Транзакция кратковременно блокирует изменения исходного
каталога, семантических сопоставлений и трёх справочников; чтение остаётся доступным.
Все предпосылки проверяются до изменения каталогов, поэтому один документ может
подтвердить единицу и сопоставление, которое на неё ссылается.

Изменение исходного определения поля, его сопоставления или связанных справочников
после экспорта делает решение устаревшим. В таком случае нужно экспортировать
новый снимок и повторно проверить решение. Ошибка любого элемента откатывает
весь пакет, включая созданные элементы и записи журнала. Пропуски identity-ID
после пробных запусков допустимы.

Повторная загрузка того же документа распознаётся по SHA256 канонического JSON
и возвращает уже существующий review_id без новых изменений. Порядок ключей
и форматирование файла не влияют на SHA; изменение текста решения влияет.
Повторное применение не восстанавливает сопоставления, которые затем были
изменены другой проверкой: для этого требуется новое явное решение.
Дублирующие ключи JSON и повторяющиеся решения одного объекта в пакете запрещены.

## История и совместимость

`semantic_review_batch` хранит документ, его SHA256, эксперта, обоснование,
время и фактического пользователя PostgreSQL. `semantic_review_change` содержит
состояния до/после; для сопоставления сохраняются также исходное поле и связанные
каталоги. Сведения доступны через `v_semantic_review_history`:

```sql
SELECT semantic_review_id,reviewer,evidence,reviewed_at,applied_by,
       object_kind,object_key,before_state,after_state
FROM geochem.v_semantic_review_history
WHERE object_kind='mapping'
ORDER BY semantic_review_id DESC;
```

UPDATE/DELETE записей журнала блокируются триггерами. Для исправления решения
создают новый экспорт и новую проверку. Администратор с полными правами технически
может менять DDL/триггеры; это не система криптографически подписанного аудита.
История фиксируется при работе через эту команду: прежний прямой SQL не становится
ретроспективно зарегистрированным. Readonly читает историю, но не пишет в неё.

Изменяются только справочники и сопоставления. Исходные названия, числовые/
текстовые значения, группы, повторы, единицы источника и raw_cells сохраняются.
Аналитические представления сразу показывают новое сопоставление; старые запросы
приложения работают с теми же источниками. Отдельная материализация не требуется.

## Проверки

```powershell
.venv/Scripts/python.exe -m autopyro.database.tools.validate_catalog_review
.venv/Scripts/python.exe -m pytest tests/test_catalog_review.py -q
```

Интеграционная проверка с откатом испытывает создание канонического элемента,
подтверждение единицы, переназначение поля, защиту от устаревшего решения,
повторный запуск, откат частично ошибочного пакета, защиту истории и readonly.
Сравниваются отпечатки всех существующих таблиц до/после теста. Синтетические
научные решения не сохраняются. На текущей базе применена только миграция 014;
реальные экспертные решения пока не внесены.
