# Единый запуск миграций

Команда `autopyro.database.tools.migrate` обновляет существующую базовую схему
и ведёт журнал `geochem.schema_migration`: имя SQL-файла, SHA256, время и роль,
выполнившую миграцию. Пароли читаются из локального `.env`/переменных окружения
тем же способом, что и в других административных утилитах, и не выводятся.
По умолчанию используется `admin`; PGHOST/PGPORT/PGDATABASE/PGUSER/PGPASSWORD
позволяют выбрать подключение явно.

```powershell
# Показать применённые и ожидающие миграции, ничего не менять:
.venv/Scripts/python.exe -m autopyro.database.tools.migrate

# Проверить актуальность для скриптов/CI:
.venv/Scripts/python.exe -m autopyro.database.tools.migrate --check

# Применить все ожидающие миграции одной транзакцией:
.venv/Scripts/python.exe -m autopyro.database.tools.migrate --apply
```

Коды завершения: 0 — успех; 1 — есть ожидающие миграции при `--check`;
2 — ошибка базы, контрольной суммы или структуры истории.
План и `--check` выполняются в read-only транзакции и не создают журнал.

## Первый запуск на существующей базе

До появления журнала отдельные миграции применялись вручную. Команда не выдаёт
их за исторически проверенные: при первом `--apply` она повторно выполняет
текущие идемпотентные SQL 002, 003 и 005–010 и записывает именно эту операцию.
Их повторное применение проверено на текущей базе с откатом и сравнением
отпечатков существующих таблиц. Ручные сопоставления, выбранные версии,
аннотации качества и пользовательские интерпретации сохраняются.
История показывает время повторного применения, а не даты старых ручных запусков.
Новые строки источников, ещё не включённые в справочники или снимки, могут
получить соответствующие записи при таком заполнении.

После регистрации выполненные миграции пропускаются. Поэтому команда не служит
постоянным обновлением каталогов/импортом: эти действия выполняют импортёры
и соответствующие функции refresh/snapshot.

## Правила дальнейшего развития

- Существующий SQL-файл после регистрации не редактируют: исправление оформляют
  новым файлом `NNN_description.sql` в `database/migrations`.
- Номера должны быть уникальны, имена соответствовать шаблону из трёх цифр,
  подчёркивания, строчных латинских букв/цифр/подчёркиваний и `.sql`.
- SHA256 рассчитывается по UTF-8 без BOM с нормализованными переводами строк:
  смена CRLF/LF не создаёт ложного изменения. Остальное содержимое, включая
  комментарии, входит в контрольную сумму.
- Отсутствующий локальный файл, изменение контрольной суммы или пропуск внутри
  уже зарегистрированной последовательности останавливают запуск.
- Новые миграции должны поддерживать выполнение в общей транзакции. Команда
  снимает необязательную внешнюю пару BEGIN/COMMIT текущих SQL-файлов; операции
  вроде CREATE INDEX CONCURRENTLY для такого запуска не подходят.

Общая транзакционная advisory-блокировка сериализует экземпляры этой команды.
При ошибке откатываются все изменения текущего пакета и его записи журнала.
Пропуски identity-последовательностей при откате допустимы.
Проверять и применять обновления следует без параллельного изменения схемы
старыми отдельными командами; они не участвуют в общей блокировке.

Контрольные суммы подтверждают неизменность зарегистрированных файлов, но
не обнаруживают ручной ALTER TABLE/отключение триггеров или правку самого журнала
администратором. Для проверки поведения остаются специализированные валидаторы.

## Базовая схема и доступ

Команда требует уже созданной `geochem` с базовой схемой `database/schema.sql`.
В Compose она создаётся автоматически при первом запуске пустого тома.
При необходимости базовую схему применяют отдельно. Импорт данных — отдельный шаг.

Миграция `004_readonly_access.sql` исключена из этого запуска: создание/переименование
ролей и настройка доступа остаются за `configure_users.py` по [ACCESS.md](ACCESS.md).
Команда миграций не меняет пароль и не создаёт роли. При существующей роли
`readonly` ей предоставляется SELECT на журнал, а новые миграции следуют
установленным правилам доступа. Повторное применение 004 при обычном обновлении
не требуется. Команды подготовки ролей и схемы выполняются отдельно и последовательно.

## Проверки

```powershell
.venv/Scripts/python.exe -m autopyro.database.tools.validate_migrations
.venv/Scripts/python.exe -m pytest tests/test_schema_migrations.py -q
```

Валидатор проверяет реальное применение и откат намеренно ошибочного пакета,
повторный запуск, неизменность строк существующих таблиц, контрольные суммы,
пропавшие файлы, пропуски истории и просмотр плана ролью readonly.
Все изменения валидатора откатываются. Тесты на файлах отдельно проверяют
переводы строк, снятие оболочки транзакции, некорректные номера и исключение 004.
