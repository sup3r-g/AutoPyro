# Общий справочник стволов

Миграция `006_unified_wellbores.sql` требует установленной миграции 003.
Она добавляет `wellbore` и две таблицы сопоставления:
`well_wellbore_link` и `lithostrat_wellbore_link`. Старые таблицы и связи не меняются.
Имя не является уникальным идентификатором ствола: стабильный ключ — `wellbore_id`,
а `code` сохраняет происхождение автоматически созданной записи.

Каждая запись `well` получает самостоятельный ствол. Литостратиграфическая запись
связывается сначала по существующему `well_id`, затем по точному названию, только
если ему соответствует ровно одна запись `well`. Иначе создаётся отдельный ствол.
Пробелы, регистр и суффиксы имён не нормализуются автоматически. Совпадающие имена
не приводят к автоматическому объединению нескольких записей `well`.

Все связи изначально `reviewed=false`. После проверки эксперт может переназначить
ссылки на общий `wellbore_id`, выставить `reviewed=true` и для литостратиграфической
связи `match_basis='manual'`. Исходные идентификаторы сохраняются.
Повторное заполнение существующие сопоставления не изменяет. Если ранее отдельный
ствол получил возможное соответствие после нового импорта, его объединяют вручную.
Старые приложения продолжают читать старые связи; решения эксперта в новом слое
отображаются только в новых представлениях. Новые запросы должны использовать его
как основной источник идентификации ствола.

## Представления и глубины

- `v_sample_wellbore`: все исходные поля пробы, общий идентификатор ствола,
  признак проверки связи, `depth_type='MD'`, `depth_unit='m'`, исходный `md_datum`.
- `v_lithostratigraphy_wellbore`: прежнее представление литостратиграфии плюс общий
  идентификатор, основание сопоставления, признак проверки, метры и неизвестные
  `depth_type`/`depth_datum`. Исходное поле `depth_reference` сохраняется.

У проб без `well_id` общий ствол остаётся NULL. Количество строк обоих представлений
совпадает с количеством строк соответствующих исходных таблиц. Определение MD для
проб следует из названий исходных колонок Top MD/Base MD, а не из предположения о Excel.
Тип глубины и datum Excel ещё требуют внешнего подтверждения. Присоединять пробы
к интервалам только по числовому попаданию в диапазон нельзя без этой проверки.
Преобразование MD/TVD, псевдонимы и версии стратиграфических интерпретаций в эту
миграцию не входят.

```sql
SELECT s.sample_id, s.wellbore_id, s.wellbore_name, s.top_md, s.base_md,
       s.depth_type, s.depth_datum
FROM geochem.v_sample_wellbore s
ORDER BY s.wellbore_id, s.top_md;

SELECT wellbore_id, wellbore_name, unit_name, top_depth_m, bottom_depth_m,
       depth_type, depth_datum, match_basis
FROM geochem.v_lithostratigraphy_wellbore
ORDER BY wellbore_id, top_depth_m;
```

## Применение

```powershell
.venv/Scripts/python.exe -m autopyro.database.tools.validate_wellbore_catalog
.venv/Scripts/python.exe -m autopyro.database.tools.validate_wellbore_catalog --apply
```

Проверка сравнивает агрегированные отпечатки и количество строк старых таблиц,
полноту связей, количество строк представлений, отсутствие выдуманной системы
глубин Excel, сохранение ручных решений, повторяемость миграции и SELECT readonly.
Первый запуск откатывает изменения, второй фиксирует после успешных проверок.
Применять при отсутствии параллельного изменения исходных таблиц.

После установки оба импортёра вызывают `refresh_wellbore_catalog()` перед фиксацией.
После ручного добавления источников функцию нужно вызвать явно:

```sql
SELECT geochem.refresh_wellbore_catalog();
```

Для пустой базы сначала импортируйте литостратиграфию (создаётся схема 003), затем
примените 006. Миграция 006 намеренно не подключена к начальной загрузке Compose,
поскольку таблицы Excel в ней ещё могут отсутствовать.
